# DSH 酒馆的 Docker 镜像

`docker-tavern/` 目录和它的构建流程把 [DSH 酒馆](https://github.com/flizzywine/dsh-tavern)
的命令行版做成镜像 `ghcr.io/pandyzhou/dsh-tavern`。容器启动后，打开地址先看到登录页，
输入账号密码后进到酒馆界面。

它和 `docker/` 里的 dsh 镜像是两个独立的镜像：酒馆的命令行版只认它自己锁定的那一版
DeepSeek Harness，所以自带一份，不和原版 dsh 共用。两个都想用就各跑一个容器。

## 镜像里有什么

- 构建时运行酒馆官方的安装脚本，固定在 `TAVERN_COMMIT` 里写的那个提交上，把装好的
  结果打包放进镜像。
- 容器第一次启动时把它解包到数据目录 `/data`，约 1.7 GB。之后它就是一份标准的命令行
  版安装：程序、人物卡、聊天、设置都在数据目录里，酒馆页面里的“检查更新”照常可用。
- 酒馆只在容器内部监听。对外的端口 3081 是一道“门”（`support/gate.cjs`）：它提供
  登录页，把已登录的请求转给酒馆。对外是普通的 HTTP，由前面的反向代理负责 HTTPS。
- 入口脚本守着服务：服务退出，容器跟着退出，交给 Docker 重启；在页面里更新或用命令
  重启服务时，容器不动。

## 使用

参考 `compose.yaml`，反向代理参考 `openresty.conf`。启动后打开地址，用设置的账号密码
登录。第一次进去时会先弹出 DeepSeek Harness 的“预览版说明”，点“继续”即可。

进去之后还要做两件事才能玩：

1. 左侧栏底部的 设置 → 模型 里填服务地址、API 密钥和模型名。
2. 导入一张人物卡（PNG 或 JSON），新建游玩。

反向代理要做到三点：原样转发 `Host`、转发 WebSocket 升级请求、对外用 HTTPS。上传的
人物卡和素材可能很大，请求体的大小上限也要放宽。不需要在反向代理上再加密码。

环境变量：

| 变量 | 作用 |
|---|---|
| `DSH_LOGIN_PASSWORD` | 登录页的密码，必须设置，至少 8 个字符 |
| `DSH_LOGIN_USER` | 登录页的账号，默认 `tavern` |
| `DSH_PUBLIC_URL` | 通过反向代理访问的地址，例如 `https://tavern.example.com/`。酒馆只在告诉过它的域名下工作 |
| `DSH_TRUSTED_HOSTS` | 另外还要用到的域名，多个用空格隔开；不是 80 或 443 端口时写成 `域名:端口` |
| `DSH_TAVERN_PORT` | 登录页的端口，也就是要发布出去的端口，默认 3081 |
| `DSH_TAVERN_BIND` | 登录页监听的地址，默认是容器的所有地址 |

用没列进 `DSH_PUBLIC_URL` 和 `DSH_TRUSTED_HOSTS` 的域名访问时，能登录，但酒馆会以 403
拒绝之后的请求。直接用 `127.0.0.1` 或 `localhost` 访问不受这个限制。

## 登录

- 登录保持 30 天，使用中每天自动续期一次，所以常用的浏览器不会掉登录。
- 登录状态记在浏览器的 Cookie 里，只对登录时用的那个域名有效，容器重启后仍然有效。
- 10 分钟内输错 10 次，登录页会锁到这些错误过了 10 分钟为止；已经登录的不受影响。
- 改了账号或密码再启动，原来所有的登录都失效。
- 密码只在容器启动的那一刻用到：之后容器里运行的程序（酒馆和它的 Agent）拿到的是
  由密码算出来的值，拿不到密码本身。

酒馆（DSH）自己的登录方式是启动时打印一条带令牌的链接。这个机制还在容器内部，由
“门”自己去用，外面用不了：带令牌的请求会被“门”挡回登录页，日志里也不再打印链接。

人物卡画在和页面隔离开的小窗口里，浏览器不会给小窗口发出的请求带上 Cookie。酒馆
为此留了几个不用登录就能读取的资源地址，“门”对没登录的读取请求不带任何 Cookie 地
转给酒馆，由酒馆自己决定放不放行。所以这几个地址对知道域名的人是开放的，和酒馆
本来的行为一样。

## 数据

全部在 `/data` 一个目录里：

- `/data/dsh-tavern/profile-data`：人物卡、聊天、插件
- `/data/dsh-tavern/settings.yaml`、`/data/dsh-tavern/.credentials.yaml`：设置和密钥
- `/data/dsh-tavern/profiles/tavern/cordis.patch.yml`：模型和服务商
- `/data/.login-secret`：登录用的随机密钥。删掉它，所有登录都失效
- 其余是程序本身（酒馆、它的 DSH、依赖）和包管理器的缓存，丢了可以再装回来

## 更新和修复

- **更新酒馆**：用酒馆页面里的“检查更新”，或者
  `docker exec dsh-tavern dsh-tavern update`。更新走官方安装脚本，装的是上游主分支的
  最新提交。
- **换新镜像**：只更新系统、Node 和启动脚本。数据目录里已经装好的酒馆不会被换掉，
  镜像自带的那一份只在数据目录里没有酒馆时放进去。
- **修复**：程序文件坏了的时候，停掉容器后执行
  `docker run --rm -v "$PWD/data:/data" ghcr.io/pandyzhou/dsh-tavern repair`，把镜像自带
  的程序放回去。人物卡、聊天、设置和密钥不动；之后可以再在页面里更新。程序文件缺失
  时，容器启动时也会自动这样做；更新到一半容器被停掉的，下次启动会先退回更新前的版本。
- **其他命令**：`docker exec dsh-tavern dsh-tavern status` 查看状态，`restart` 重启
  服务。`stop` 之后容器会随之退出。
- **镜像自带的版本**：
  `docker run --rm --entrypoint cat ghcr.io/pandyzhou/dsh-tavern /opt/dsh-tavern/seed.json`。

## 安全

酒馆把 Agent 的权限全部打开，执行命令不再询问，所以能登录的人等于能在容器里执行
任意命令。上游的文档只建议在可信内网或 VPN 里使用命令行版。放到公网域名后面时：

- 密码要够长，不要和别处共用；
- 端口只绑在 `127.0.0.1`，只让反向代理访问；
- 容器里的 Agent 能改的只有容器和数据目录里的东西。

## 构建

`.github/workflows/docker-tavern-image.yml`：改动 `docker-tavern/` 后自动构建，也可以
手动运行。酒馆用哪个提交写在 `TAVERN_COMMIT` 里；只改脚本时预装这一步用的是缓存，
换提交号时才会重装。

构建后先把容器按部署的方式跑起来（`smoke-test.sh`），全部通过才推送。检查的内容：

- 没设密码或设置不对就不启动；
- 没登录进不去，酒馆自己的令牌链接从外面无效；登录后打开的是酒馆，酒馆的 Cookie
  不会到浏览器，服务不以 root 身份运行，容器里的程序拿不到密码；
- 给出的域名放行，没给出的域名、别的站点发起的请求被拒绝；登录只对它的域名有效；
- 把 `openresty.conf` 原样放在镜像前面，用真的浏览器登录：能进到酒馆，连接保持正常，
  隔离的小窗口取得到免登录的资源、取不到需要登录的内容；
- 重启后数据和登录状态都在，不会重新解包；
- 用命令重启服务、在容器里更新酒馆时，容器不动，更新后数据还在；
- 服务异常退出后容器退出；上一个容器留下的锁和记录不妨碍启动；更新中断后能退回；
- 程序文件缺失时自动放回，`repair` 命令同样有效；
- 换了密码以后原来的登录全部失效；连续输错密码会锁住登录页；
- 在宿主机目录和 Docker 卷上都能完成首次启动。

浏览器登录这一步会把登录页和首屏的截图存成这次构建的产物 `pictures`，可以在 Actions
的运行页面下载。

推送两个标签：`酒馆版本-提交号前七位` 和 `latest`。
